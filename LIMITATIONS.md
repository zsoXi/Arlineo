# Arlineo limitations

Arlineo extracts facts with hand-written lexers and pattern matching, without running the code, without a compiler, and without type inference. This list is the current set of known limitations from `SPEC.md` section 21. Each item says what is missed or guessed, shows a short example, and gives the workaround when there is one. Confidence levels (`README.md`, "Confidence levels") say how much of an answer rests on a guess.

## 1. No type inference: method calls resolve by name only

Arlineo does not know the type of a value, so a method call such as `order.save()` is resolved by the method name alone. When exactly one method in the code has that name, the edge is `unique_name`; when 2 to 8 methods share the name, the call gets one `guessed` edge to each of them; with more candidates it gets no edge. Common standard library method names (for example `clone`, `map`, `push`, `get`, `toString`, `parse`) never get `unique_name` or `guessed` edges at all.

```rust
// Two types have a save method. A call through a value of either type
// cannot be attributed to one of them; both become guessed targets.
order.save();
```

```ts
// Same in TypeScript: the receiver type is not known.
customer.save();
```

Workaround: none. Read `guessed` and `unique_name` edges as candidates to check, not as proven calls. Calls through `self`, `Self::`, qualified paths and imports are resolved exactly and are not affected.

## 2. Macros: items generated by macros are not seen

Calls inside macro arguments are extracted, because the macro's token tree is scanned like other code. But items a macro generates when it expands do not exist in the source as written, so Arlineo never sees them: a function, type or route that only exists after expansion has no fact.

```rust
// The call inside the argument is extracted.
println!("total: {}", compute_total(order));

// If a macro invocation generates a function, that function is not
// extracted, because its tokens are produced by the macro, not written here.
make_handler!(list_orders);
```

Workaround: none. Where generated code matters, write the generated item out as real source, or treat the macro invocation site as the place to look.

## 3. Route prefixes from nested routers are not joined

When a router is mounted under a prefix by the framework, Arlineo does not join that prefix onto the routes registered inside the router. The route is recorded with the path as written at its registration, so it will not match API calls that use the mounted path.

```rust
// The route is recorded as /orders, not /api/orders.
let api = Router::new().route("/orders", get(list_orders));
let app = Router::new().nest("/api", api);
```

Workaround: set the pattern's `prefix` option to the mounted prefix (see `RULES.md`, "Route patterns"). With `"prefix": "/api"` the route above is recorded as `/api/orders`. Nested mounts of different depths under one pattern cannot be expressed this way.

## 4. SQL: PostgreSQL only; dynamic SQL is not seen

Only PostgreSQL SQL is parsed, in `.sql` files and in string literals that look like SQL. SQL that is built at runtime - concatenated, formatted, or assembled from variables - is not a literal, so the statements it will run are not seen. SQL in strings is recognized only when the literal's text starts with `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `WITH`, `MERGE` or `TRUNCATE` after trimming, and only the tables named by the patterns Arlineo recognizes are recorded.

```rust
// The table name arrives at runtime; no table access is recorded.
let sql = format!("SELECT * FROM {table} WHERE id = $1");
```

```ts
// Built by concatenation: not a literal, so it is not seen.
const sql = "SELECT * FROM " + tableName;
```

Workaround: keep statements as whole literals where the tables matter, so they are recorded as `sql_in_code` and `table_access` facts with `heuristic` confidence. SQL for other databases is lexed as PostgreSQL and may be misread.

One dynamic form is read: `EXECUTE format('GRANT ...', args)` in a SQL function or `DO` body, when every argument is a string literal or the variable of an enclosing `FOREACH v IN ARRAY ARRAY['a', ...] LOOP` over string literals; it gives one grant per value. Only the conditions `IF v IN ('a', ...)` and `IF v = 'a'` on the loop variable narrow those values; under any other condition (for example `IF v <> 'a'`, or an `ELSE` branch) every value gets the grant, which can give a missing-grant hit that is not real. A grant whose object or role comes from a query loop (`FOR t IN SELECT ...`) or an expression is not seen: `sources-agree` then reports the grants it would cover as missing. List those in the rule's `ignore` with the loop's `file:line` as the reason.

A later `DROP TABLE` ends the grants on that table through the rule's `dropped` selector, by name only, together with the sequences of its identity and `serial` columns under their default name `<table>_<column>_seq`. A sequence named in `GENERATED ... AS IDENTITY (SEQUENCE NAME ...)`, a name PostgreSQL shortens past 63 characters, a sequence tied to a table by `ALTER SEQUENCE ... OWNED BY` or by `ALTER COLUMN ... ADD GENERATED`, and a `DROP SEQUENCE` are not read, so a grant on such a sequence still needs a matching grant on the right side of the rule, or an `ignore` entry.

## 5. TypeScript path aliases are not resolved

Imports through a path alias configured in `tsconfig.json` (for example `@/`) are recorded as written, but the alias is not mapped to a directory. Calls through such an import therefore do not get an `exact` edge to the imported function; they fall back to resolution by name (`unique_name` or `guessed`).

```json
{
  "compilerOptions": {
    "paths": { "@/*": ["web/src/*"] }
  }
}
```

```ts
// Recorded with the specifier @/api/orders; the alias is not resolved,
// so calls through this import resolve by name only.
import { listOrders } from "@/api/orders";
```

Workaround: none in configuration. Relative specifiers (`./orders`, `../orders`) are resolved against the importing file and give `exact` edges; using relative imports where the call graph matters keeps those edges exact.

## 6. Template literal expressions are not scanned for calls

A template literal is one token. Its `${ ... }` expressions are not scanned for calls, so a function called only inside a template expression has no call fact from that place. For SQL recognition, a template is read with every `${...}` replaced by `${}`, so a table name or condition that only exists inside an expression is not seen either.

```ts
// formatPrice is called, but the call is inside a template expression
// and is not extracted.
const label = `total: ${formatPrice(order.total)}`;
```

```ts
// Read as SQL over orders with a ${} placeholder; a table named only
// inside the expression would not be recorded.
const sql = `SELECT * FROM orders WHERE id = ${orderId}`;
```

Workaround: none. Move a call out of the template into a variable first when the call must appear in the graph.

## 7. TypeScript without semicolons is read approximately

JavaScript ends a statement at a line break when the next line cannot continue it (automatic semicolon insertion). Arlineo approximates this rule: a line break ends a declaration, a class field or a type alias unless the line before ends with an operator, `(`, `,`, `=>` or a keyword such as `await`, or the next line starts with punctuation such as `.`, `?`, `(` or `[`, or with `as`, `in` or `instanceof`. Code that relies on the exact rule can be split differently, for example a multi-line JSX element without surrounding parentheses.

```ts
// Read as two statements, as intended.
const total = items.length
export function list() { return items }

// The attribute on the next line ends the declaration early; wrap
// multi-line JSX in parentheses, as formatters do.
const el = <div
  className="x" />
```

Workaround: use semicolons, or wrap multi-line JSX in parentheses.

## 8. TypeScript decorators are skipped

A decorator before a class member (`@Get(':id')`, `@Input()`) is skipped as a whole, so the member after it is read normally. Calls inside decorator arguments are not extracted. TypeScript code gives no routes, so a decorator such as `@Get(':id')` is not a route either.

```ts
class OrdersController {
  // findOne is recorded as a method; the call Get(':id') is not.
  @Get(':id')
  async findOne() {}
}
```

Workaround: none; routes are read only from Rust.

## 9. Default imports resolve through `default` or the local name

`import list from './orders'` is resolved to the function exported as `default`, or to a function in `./orders` whose name equals the local name `list`. A default export imported under a different name (`export default function listOrders` imported as `list`) resolves by name only.

Workaround: import a default export under its own name, or use a named export.

## 10. Rust qualified paths `<T as Trait>::m` resolve by the method name

For `<Order as Named>::label(&order)` the call is recorded with name `label` and no qualifier, so it resolves like a bare call: a function `label` in the same module or brought in by `use`, else by name (`unique_name` or `guessed`).

Workaround: none.

## 11. The overlay cache trusts size and modification time

A worktree's changed files are read again only when their size or modification time changed since the cached read, or when they were modified in the last 2 seconds. A tool that rewrites a file with the same size and restores its old modification time leaves stale facts in the overlay.

Workaround: change the file's modification time (for example with `touch`), or remove the worktree's `overlay/<worktree-id>/` directory from the store.

## 12. `requires-before` holds when some path has the requirement

The rule holds when the owner itself, or any caller within `depth`, has the required fact. Other callers without the requirement give no hit, the order of the two facts is not checked, and `guessed` call edges count. `RULES.md` ("`requires-before`") explains this in detail.

Workaround: set `all_paths`, so every caller chain must take the requirement before the call, without `guessed` edges. Chains are followed only up to `depth`, a chain that reaches `depth` counts as missing the requirement, and a function that calls a helper which takes the requirement counts only when the helper has the `require` fact itself (one level). A chain cut by `depth`, ending at a function reached only by `guessed` edges, or ending in a call cycle, is reported as uncertain and not counted, so a real gap behind a guessed caller, deeper than `depth` or entered through a cycle shows only in the uncertain list. A `guessed` caller is ignored altogether when the function also has at least one other caller: only the other callers' chains are checked.

## 13. Top-level SQL and `DO` blocks have no graph node

Statements at the top level of a `.sql` file and inside `DO` blocks give `table_access` facts (owned by the file and by `<file>#do@<line>`), but no node exists for these owners, so they give no `reads` or `writes` edges. `impact` and graph walks do not reach them; `table` and `find` still list the facts.

```sql
-- A table_access fact (delete on sessions), but no writes edge.
DELETE FROM sessions WHERE expired;
```

Workaround: use `arlineo find --kind table_access --where key=sessions` to list them.

## 14. Queries answer from the line unless `--worktree` is given

Without `--worktree`, `find`, `table`, `route`, `fn`, `graph` and `impact` answer from the line's index only, so files changed in a worktree, committed or not, are not part of the answer. The stamp says which view an answer comes from.

Workaround: pass `--worktree <path|directory|branch>` when the question is about your own changes.
